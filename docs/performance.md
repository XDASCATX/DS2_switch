# Производительность: инструменты, замеры, метод

Цель владельца: **стабильные 30+ кадр/с везде** (Маджула, бой, подгрузка), желательно без предельного разгона.

## 1. Инструменты измерения (все — на консоли, без отладчика)

| Инструмент | Где в коде | Включение | Что даёт |
|---|---|---|---|
| Профайлер процесса | `sdk/src/ui/switch_perf.cpp` | всегда; стеки — `ds2_switch_stack_sampling` | `logs/rex/rex_perfil.log` раз в 10 с: FPS игры, CPU каждого потока (точно, по тикам ядра), выборка pc/lr/стека 1 кГц, частоты CPU/GPU/EMC, температура, вызовы libnx (fences, kickoff, NvMap, окно) |
| Статистика нативного рендерера | `NativeCommandProcessor::LogStats` | `ds2_native_log_every` (300 кадров) | `[native] per frame`: draws/resolves/passes/upload; `cpu ms per frame`: поток команд (ожидание GPU, draws, текстуры, шейдеры, resolve); `early-z`, асинхронные конвейеры |
| Профиль GPU по проходам | `Mark/MarkPass/CollectProfile` | `ds2_native_gpu_profile` | метки времени вокруг каждого прохода/копии/очистки/загрузки: `[native gpu] GPU ms per frame` и топ-16 видов прохода (размер, шаг, MSAA, форматы) |
| Профиль GPU по вызовам | там же | `ds2_native_gpu_draw_profile_every = N` (v56) | раз в N кадров метка на каждый draw: `[native gpu draws]` — топ-30 пар шейдеров (vs/ps), число вызовов и вершин |
| Журнал рывков | `IssueSwap` | `ds2_native_hitch_ms` (100) | `[native] hitch`: на что ушёл долгий кадр (GPU, draws, текстуры, шейдеры, resolve, «вне потока команд») |
| Снимок кадра | `PollDumpCombo/DumpImages` | L3+R3 (`ds2_native_capture_combo`) | трасса всех draw/resolve кадра + изображения RT/resolve |
| Счётчики вызовов функций игры | `REX_FUNC_COUNT`, `app/src/ds2_func_counts.cpp` | `ds2_func_counts` | `logs/ds2_llamadas.bin`, декодер `tools/analysis/ds2_func_counts.py` |

| Зоны GPU эмуляции (до v51) | `sdk/src/graphics/vulkan/command_processor.cpp` | `gpu_zone_timing*` | только эмуляционный путь |

Таймер GPU на Switch: NVK сообщает период 1 нс, реальный счётчик — 614,4 МГц (как NVN: ticks·625/384).
С v55 код пересчитывает (до v55 цифры `[native gpu]` занижены в 1,63 раза). **[замер v54: сумма GPU-времени ×1,63
совпала с длиной кадра]**

## 2. Как искать узкое место (метод, который сработал)

1. `rex_perfil.log`: у потока `GPU Commands` смотреть CPU % и долю `svcWaitSynchronization`
   (`threads.py --thread "GPU Commands"`). Много ожидания fence + `waiting for the GPU` в `cpu ms per frame` →
   предел **GPU**; тогда — `[native gpu]` по проходам и `[native gpu draws]` по шейдерам.
2. Если поток команд почти не ждёт GPU, а кадр длиннее, чем GPU-время → предел **CPU**: смотреть CPU потока
   команд (IssueDraw, выделения памяти, запись регистров) и главного потока игры (стеки:
   `svcArbitrateLock` = конкуренция за мьютекс, `sub_829E9E28` / `sub_829D8408` = D3D игры ждёт GPU/поток команд).
3. Менять одну вещь за раз, оставлять ключ TOML для отката, мерить в тех же местах на той же частоте.

## 4. Что уже дало эффект (подтверждено консолью)

- Нативный рендерер вместо эмуляции EDRAM (v53): 11–16 → 13–30 кадр/с в тех же местах.
- early-Z (`kEarlyHint`, v55): HDR-проход ~34 → 16,5 мс.
- Одна отправка на кадр (v54): ожидания fence 4 → ~2 на кадр (эффект на FPS отдельно не мерился).

## 5. Что сделано, но не проверено на консоли (v56)

Без общего мьютекса `mtmsrd`, dynamic UBO, повтор наборов текстур в кадре, быстрые пути записи регистров,
встроенная раздвижка тайлов, кэш sub-resolve, FMA в пиксельных шейдерах. Ожидание — меньше CPU у потока команд
и главного потока; величина неизвестна.

## 6. Известные резервы (не сделано)

| Идея | Ожидаемый эффект | Риск/цена | Статус |
|---|---|---|---|
| Настоящий 4xMSAA для целей 4x (G-буфер затеняется в 4 раза больше пикселей, чем на X360) | GPU −5…8 мс **[вывод]** | нужны конверсии 1x↔4x на общей базе EDRAM (DS2 переинтерпретирует глубину 4x 640 как 1x 1280) | не начато |
| Кэш вершинных буферов между кадрами (сейчас 10–13 МБ копий на кадр) | CPU потока команд −3…5 мс **[вывод]** | нужна проверка записи CPU (хеш) | не начато |
| Push-дескрипторы (VK_KHR_push_descriptor) | меньше malloc в NVK | нужна правка создания устройства SDK | не начато |
| Офлайн-библиотека шейдеров (XenosRecomp + DXC, как NFSMW-NX) | быстрее пиксельные шейдеры, нет рывков компиляции | большая работа; см. handoff/18-native-renderer-study | исследовано |
| 32-битный формат HDR (B10G11R11) вместо RGBA16F | меньше полосы в HDR-проходе | у оригинала 2 бита альфы; конверсии 7e3 | не начато |
| Оптимизация главного потока игры (код рекомпиляции) | при пределе CPU | codegen-уровень | не начато |
