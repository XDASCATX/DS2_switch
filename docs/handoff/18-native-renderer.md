# Нативный рендерер DS2 (v51, экспериментальный)

## Зачем

Измерено в v48–v50 (Маджула/Лес, 11–16 кадр/с): видеочип занят 60–90 мс на кадр, из них 20–29 мс — переносы
между видами EDRAM, ~11 мс — resolve, ~6,5 мс — повторная загрузка тех же данных в текстуры. Главный поток игры
95 % времени крутится в ожидании GPU внутри Direct3D игры (`sub_829E9E28`, `sub_829D8408` — циклы `db16cyc`), то
есть процессор не предел — предел эмуляция EDRAM. NFSMW-NX получил 30+ кадр/с тем же путём: свой графический
модуль вместо эмуляции Xenos.

## Выбор технологии

- **deko3d** (rexglue-sdk-nx) — в нашем toolchain его нет (ни `libdeko3d`, ни `uam`), шейдеры пришлось бы
  переводить в GLSL и компилировать `uam`; рендерер rexglue-sdk-nx пока доводит только Halo до меню.
- **Vulkan на NVK** — уже работает в порте, NFSMW-NX показал, что на нём достижимы 30+ кадр/с. Выбран он.
- Шейдеры: на первом шаге — переводчик SDK (микрокод Xenos → SPIR-V во время игры, тот же, что у эмуляции и уже
  проверен на DS2). Офлайн-библиотека (XenosRecomp + DXC, как в NFSMW-NX) — следующий шаг для скорости.

## Архитектура (sdk/src/graphics/native/native_renderer.cpp)

Отдельный графический модуль рядом с эмуляцией. Выбор: `ds2_native_renderer = true` в TOML; по умолчанию —
прежняя эмуляция (fallback, v50 без изменений).

| Часть | Как сделано |
|---|---|
| Кольцо PM4, регистры, ожидания, прерывания, vblank | базовый `CommandProcessor`/`GraphicsSystem` SDK (проверены на DS2) |
| Шейдеры | `SpirvShaderTranslator` SDK; модули кешируются по хешу микрокода и модификации |
| Вершины и индексы | копия нужных диапазонов памяти игры в буфер кадра (48 МБ × 3); fetch-константы переписаны на смещения в нём; порядок байт меняет шейдер, как в эмуляции |
| Render target | обычные Vulkan-изображения по (база EDRAM, шаг, формат); MSAA — в пространстве сэмплов: 4x 640×360 = изображение 1280×720, поэтому 1x и 4x-виды одной области EDRAM (тени DS2, половинное разрешение) — одно и то же изображение, без переносов |
| Resolve | копия изображения в «нативную текстуру» по адресу назначения; выборка текстуры с этого адреса берёт её напрямую, память игры не трогается |
| Текстуры игры | раздвижка тайлов на CPU в изображение, кеш по fetch-константе, проверка хеша раз в 30 кадров |
| Очистки | `vkCmdClearAttachments` по прямоугольнику resolve |
| Показ кадра | resolve-изображение по адресу из fetch-константы 0 копируется в изображение презентера |
| Примитивы | треугольники, полосы, веера, линии; прямоугольники и точки — режимы переводчика (4 вершины в полосе); квады — индексы на CPU |

## Что проверено (PC, lavapipe; на консоли ещё не запускалось)

- Игра идёт с нативным модулем: логотипы, предупреждение об автосохранении, титульный экран, меню «Data List» —
  картинка правильная (v51).
- В игре (Междумирье, загрузка сохранения): с v52 сцена, освещение, небо, персонаж и HUD выглядят правильно
  (снимок не в репозитории — скриншот игры; на Mac: `switch/v52/pc_native_frame.png`). Эмуляция на том же PC даёт красный оттенок, то есть
  нативный путь на PC уже точнее эмуляции.
- Кадр DS2 (Междумирье, ~480–620 вызовов отрисовки): 23 RT-изображения, 22 resolve, ~9 МБ вершин и индексов на
  кадр, 118 конвейеров.

## Как устроен кадр DS2 (измерено нативной трассой, `ds2_native_dump_dir` + `ds2_native_dump_swap`)

1. Тени: глубина D24S8 4xMSAA 400×400 (= 800×800 сэмплов), resolve в атлас 1600×1600 по четвертям (Direct3D сдвигает
   базу назначения на тайл точки назначения — нативный resolve находит текстуру-владельца и тайл).
2. G-буфер: цвет 8888 + глубина D24FS8 в 4xMSAA 640×360 (= 1280×720 сэмплов), resolve нормалей и глубины;
   глубина резолвится с форматом назначения k_8_8_8_8, но читается как k_24_8_FLOAT.
3. Буфер света: очистка через глубину (D24S8 z=1, stencil=FF) и переинтерпретация как 8888 (= белый),
   затем источники света умножают (`exp(-свет)`, смешивание DST_COLOR×ZERO).
4. Освещение сцены в k_2_10_10_10_FLOAT (7e3), для resolve тот же EDRAM переобъявлен как k_2_10_10_10 (биты 7e3 как
   unorm), потом читается как k_2_10_10_10_AS_16_16_16_16 и декодируется шейдером.
5. Яркость (цепочка 16×16 k_16_16_16_16_FLOAT), тонмаппинг, HUD, resolve в кадровый буфер.

## Найденные и исправленные ошибки (по журналу PC-прогонов)

| Симптом | Причина | Исправление |
|---|---|---|
| сцена чёрная, HUD есть | 4xMSAA-цели как 1x пиксели: 1x/4x-виды EDRAM — разные изображения | MSAA в пространстве сэмплов |
| сцена чёрная | `k_2_10_10_10_AS_*` / `_GAMMA` — разные изображения | один ключ по формату хранения |
| HDR-текстура пустая | resolve через переобъявленный k_2_10_10_10 | переинтерпретация 7e3 ↔ unorm10 при смене формата |
| тени: 3 из 4 каскадов терялись | resolve в часть атласа | поиск текстуры-владельца по адресу и тайлу |
| красный/синий переставлены | copy_dest_swap гостевого resolve | перестановка в виде текстуры |
| глубина как текстура: G/B = 0 | глубина одна компонента | swizzle RRRR, как в эмуляции |
| голубой оттенок всей сцены | при z = 1.0 `uint(z·16777215 + 0.5)` = 2^24 переполнял биты глубины → «белый» буфер света становился красным | `round()` и ограничение 0xFFFFFF |

## Ограничения (известные)

- Переинтерпретация EDRAM между форматами — только три вида (глубина → 8888, 7e3 ↔ unorm10); остальные смены формата
  на той же базе начинаются с пустого изображения.
- Скорость на консоли неизвестна (на PC lavapipe ~0,5 кадр/с — это программный рендеринг, о Switch ничего не говорит).
- Гамма-рампа при показе кадра не применяется; знаковые форматы текстур — как беззнаковые; мипы — только базовый
  уровень; кубы и 3D-текстуры — белая заглушка.
- Пользовательские плоскости отсечения выключены; memexport не поддержан.
- Синхронизация простая (глобальный барьер на каждой смене прохода) — медленнее, чем можно.
