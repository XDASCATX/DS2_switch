# 05. Разбор 50 ошибок `UnresolvedCall`

Статус: **исследование завершено, исправление не применялось, codegen повторно не запускался.**

## Метод

1. `tools/ds2_imagedump.py` расшифровывает и распаковывает образ тем же алгоритмом, что загрузчик ReXGlue. Самопроверка: во всех 50 источниках стоит `b` ровно на цель из лога (50/50).
2. `tools/ds2_make_elf.py` оборачивает образ в ELF по адресу `0x82000000`, чтобы `llvm-objdump --triple=powerpc64-unknown-unknown` печатал гостевые адреса. VMX128 он не знает, но для переходов, прологов и эпилогов этого достаточно.
3. `tools/ds2_analyze_unresolved.py` для каждой цели собирает контекст (инструкции вокруг цели и источника) и все ссылки на неё по образу: `bl`/`b`/`bc`, 32-битные указатели в `.rdata`/`.data` (vtable), конструкции `lis+addi/ori`.
4. Для промежутков между записями PDATA, где лежат цели, отдельно обходился поток управления от каждого адреса с «входными» доказательствами (`bl`, указатель в данных, `lis+addi`), чтобы понять, частью какой функции является цель.
5. Классификация ниже сделана **вручную по дизассемблированию**. Автоклассификация анализатора грубая (38 «unclear») и служит только для сбора данных.

Общие факты:
- Все 50 источников и все 50 целей лежат **вне функций PDATA**: 47 промежутков, 9 480 байт.
- На 49 целей нет ни одного `bl`, указателя в данных или `lis+addi` (у `0x8256A7D0` есть один указатель в данных). Значит, это не самостоятельные «известные» функции, а код, достижимый только хвостовыми `b` или через vtable.

## Почему это ошибка (по исходникам SDK)

`sdk/src/codegen/phase_validate.cpp` помечает `b`/`bl`, если цель не внутри текущей функции, не точка входа, не импорт и не внутри другой функции.

`sdk/src/codegen/phase_gapfill.cpp` — единственный механизм, подбирающий код вне PDATA:
- берёт `scan.codeRegions`, режет их на сегменты по `blr` и по `b` к уже известной функции;
- каждый сегмент, который не начинается в известной функции и не похож на данные исключений, регистрирует как функцию `GAP_FILL`;
- затем обходит блоки от начала сегмента; поглощённые сегменты удаляются (`cleanupAbsorbedGapFills`).

**Гипотеза, не подтверждённая логом:** промежутки с этими целями либо не попали в `scan.codeRegions`, либо были нарезаны так, что начала нужных функций не стали началами сегментов. Подтвердить можно прогоном с `--log-level trace` и поиском строк `GapFill: split segment` / `GapFill: registered sub_` по этим адресам.

## Формат overrides в ReXGlue

Читается в `sdk/src/codegen/config.cpp`, документирован в заголовке `app/huecos.toml` NFSMW-NX. Таблица `[functions]`, ключ — адрес строкой:

```toml
[functions]
"0x823A4748" = {}                                   # самостоятельная функция, размер найдёт обход блоков
"0x82646FB0" = { end = 0x82647088 }                 # явный конец (end > адрес)
"0x82640000" = { size = 0x40 }                      # или размер; end и size взаимоисключающие
"0x82641000" = { parent = 0x82640000, size = 0x20 } # фрагмент (chunk) родителя
# опционально: name = "...", share_registers = ...
```

- Записи регистрируются в `phase_register.cpp` **первыми, с высшим приоритетом** (`FunctionAuthority::CONFIG`) — раньше PDATA и сканирования.
- По предупреждению NFSMW: `{ parent }` без размера не работает (размер 0), а с размером фрагмент всё равно может уйти отдельной функцией.
- Как NFSMW подключает `huecos.toml` к манифесту (через `includes` или иначе), нужно посмотреть в `app/nfsmw_manifest.toml` перед применением.

## Классификация всех 50 целей

Буквой `r3` обозначен первый аргумент (обычно `this`). «Пред.» — инструкция перед целью. Если перед целью стоит терминатор (`b`/`blr`/`bctr`), в неё нельзя «провалиться» сверху, значит, цель — начало кода.

### A. Адаптеры `this` с хвостовым вызовом (THUNK) — 25 целей

Шаблон: две инструкции, `lwz r3,N(r3)` или `addi r3,r3,N`, затем `b X`. Перед целью — `b` конца предыдущего такого же адаптера. Это таблицы адаптеров: каждые 8 байт отдельная функция. Источники — такие же адаптеры в соседних таблицах (например, `0x823A98A0…`), у которых есть `bl`-вызовы. Цепочка «адаптер → адаптер» — обычная для C++ (смещение к базовому классу или полю, затем хвостовой вызов).

| 823A4850 | `lwz r3,8(r3)` | `b` |

| 823A4D38 | `lwz r3,8(r3)` | `b` |

| 823DEDD8, 823DEDE0 | `lwz r3,32(r3)` | `b` |

Пример `0x823A47A8`: адаптер на 8 байт, а сразу за ним, с `0x823A47B0`, начинается обычный пролог (`mflr r12; bl <savegpr>; stwu r1,…`) — граница чёткая.

| 828C7C38 | 68 | `bctr` |

### D. Точки слияния внутри функции, у которой есть только указатель из данных — 8 целей

Перед целью **нет терминатора**: код сверху в неё проваливается. Источник лежит в том же промежутке, и обход потока управления от одного и того же адреса-владельца достигает и цели, и источника. У владельца есть только ссылки из `.rdata`/`.data` (vtable), ни одного `bl`, поэтому codegen его не знает, и переход внутри одной функции выглядит как переход «в никуда».

Пример `0x82646FF0`: перед ней `bf …; lbz r9,-16(r1); li r10,0`, сама цель — `clrlwi. r10,r10,24; bclr` (выход после цикла поиска). Источник `0x82647078` ставит `li r10,1` и прыгает туда же — это ветка «нашли». Владелец `0x82646FB0` — первая инструкция после `b` (конец предыдущей функции на `0x82646FAC`), три указателя на него в данных.

|---|---|---|---|---|
| 82646FF0 | **82646FB0** | data×3 | 0x82647088 (следующая запись PDATA) | полностью дизассемблировано |
| 826473A0 | **82647360** | data×2 | 0x82647438 (следующий адрес с указателем) | терминаторы перед владельцем и перед `end` |
| 82647758 | **82647718** | data×2 | 0x826477F0 (следующая запись PDATA) | терминаторы перед владельцем и перед `end` |
| 82647E60 | **82647E20** | data×1 | 0x82647EF8 | терминаторы перед владельцем и перед `end` |
| 82648240 | **82648200** | data×1 | 0x826482D8 | терминаторы перед владельцем и перед `end` |
| 8284B85C | **8284B7E8** | data×1 | 0x8284B878 (следующий адрес с указателем) | терминаторы перед владельцем и перед `end` |

У последних трёх цель — общий хвост `li r3,0; blr`, источник — ветка `lfs/stfs` с прыжком туда же.

### E. Точка слияния в функции без найденных ссылок — 1 цель

| Цель | Владелец | Предлагаемый `end` | Доказательство |
|---|---|---|---|
| 82CFF064 | **82CFF028** (первая инструкция после `b` на `0x82CFF024`) | 0x82CFF098 | Цикл поиска по массиву; выход «не нашли» (`li r8,-1`) проваливается в цель, ветка «нашли» (`mr r8,r10` на `0x82CFF090`) прыгает в неё же из источника `0x82CFF094`. Ссылок на `0x82CFF028` в образе не найдено: ни `bl`, ни указателя в данных, ни `lis+addi`. Возможно, адрес строится иначе, чем ищет анализатор |

Итого: 25 + 7 + 9 + 8 + 1 = **50**.

## Предлагаемое минимальное исправление (НЕ применено)

Объявить **50 точек входа** — 41 цель групп A–C и 9 владельцев групп D–E. Готовый черновик лежит в `config/ds2_overrides.proposed.toml`.

- Группы A–C: `"0xЦЕЛЬ" = {}`. Размер найдёт обход блоков: каждая функция заканчивается терминатором.
- Группы D–E: `"0xВЛАДЕЛЕЦ" = { end = … }`. Цель окажется внутри функции, и переход станет внутренним. Объявлять саму цель функцией **неправильно**: это разрезало бы чужую функцию.

Риски и что проверить перед применением:
1. **Хвостовые цели объявленных адаптеров** могут сами оказаться неизвестными, и тогда появятся новые `UnresolvedCall`. Для проверки написан `tools/ds2_classify_unresolved.py`, но он **ни разу не запускался**.
2. Полностью дизассемблированы только `0x82646FB0` и `0x82CFF028`. Для остальных владельцев проверено, что перед владельцем и перед предложенным `end` стоит терминатор (`b`/`blr`), а источник и цель лежат внутри. Что между ними нет другой функции, построчно не проверялось.
3. **Более широкая проблема (гипотеза):** в тех же промежутках есть другие адреса, на которые ссылаются только данные (например, `0x82646F28`, `0x826472D8`, `0x82647438`, `0x82647D98`, `0x82648178`, `0x8284B878`, `0x828D8A28`). Если codegen их не знает, ошибок валидации они не дают, но **не будут рекомпилированы**, и вызов через vtable во время работы упадёт. Возможно, понадобится систематический поиск «функций только из данных» по всему `.text`, а не точечные overrides.
4. Механизм пропуска в GapFill не подтверждён. Если это ошибка SDK, правильнее исправить её там. Это изменение исходников SDK, оно только с отдельного согласия.
