# 11. Switch: чёрный экран после вступительного ролика — разбор логов и диагностическая сборка

Ветка `diag/switch-level-load` (от `restore/build-env`). Рабочий NRO v1 (`e990a48`) сохранён:
`out/app-switch/releases/v1-e990a48/` и у владельца `SW1_ds2/switch/ds2.nro`. Диагностическая сборка —
`out/app-switch/releases/diag2/`, у владельца `SW1_ds2/switch/diag2/` (sha256 `be61e218…288b`).

## Что установлено по логам с консоли (`SW1_ds2/ds2_logs/`, три запуска v1)

Факты:

1. **Долгий первый запуск — установка DLC, а не шейдеры.** `ds2_001.log`: от `Loading STFS header file …/dlc/D4B91B6B…`
   (05:35:43) до `[ds2 dlc] install … -> 00000000` (05:38:52) — 3 мин 9 с распаковки пакета на SD. Во 2-м и 3-м
   запусках `already installed`. Рядом лежит `._D4B91B6B…` (файл AppleDouble от macOS): попытка установки кончается
   `Error reading STFS header: -32` — безвредно, в diag2 такие файлы пропускаются.
2. **Отчёт Atmosphère — процесс `ovlloader` (Tesla), модуль `Status-Monitor-Overlay`, не `ds2.nro`.** Тип `User Break`,
   причина Panic, результат `0x1159` = 2345-0008 = `LibnxError_NotInitialized`: оверлей сам вызвал
   `diagAbortWithResult`. Время в имени файла — 1792462199 = 05:09:59 MSK, на 25–50 мин раньше трёх запусков DS2
   (05:35, 05:52, 06:01). Связь с зависанием DS2 этим отчётом не подтверждается.
   Возможная точка взаимодействия есть: SDK (`sdk/src/ui/switch_saltynx.cpp`, из nfsmw-nx) по умолчанию подключается
   к порту SaltyNX `SaltySD` (одна сессия, нужна и оверлею), пишет блоки FPS/Reverse-NX в его общую память и временно
   отпускает `sm:`. Это не доказано как причина; в diag2 мост выключен (`ds2_switch_saltynx = false`).
3. **Все три лога обрываются, `rex_perfil.log` тоже.** Последняя строка `ds2_003.log` оборвана посреди строки
   (06:02:11); отчёты профилировщика SDK (поток с высшим приоритетом, раз в 10 с) кончаются на том же месте
   (~50 с после старта: 31 fps, 41 вызовов отрисовки на кадр, гостевая память 516/902 МБ). Значит, в этот момент
   остановился весь процесс (закрыт, убит или вся система повисла), а не только потоки игры: при дедлоке внутри игры
   профилировщик и сброс лога продолжали бы писать. Как именно закрывали игру, по логу не определить.
4. Перед обрывом: всплеск создания конвейеров Vulkan (`Creating graphics pipeline state …`) и предупреждения NVK
   `channel 2 hit native submission pressure (result=0xd5c)` = `LibnxNvidiaError_Timeout` от `nvGpuChannelKickoff`
   (очередь GPU не принимает работу): 64 раза в 05:39:30–32 (переход меню → ролик), 5 раз в 05:40:52 (за 3 с до
   обрыва `ds2_001`).
5. Ошибок шейдеров, Vulkan device lost, нехватки памяти, падений (`rex_crash.log`) в логах нет. Отсутствующие файлы
   (`KeyConfigParam.param`, `HollowLevelStatsParam.param`, `cache:\`, `install:\`) — те же, что на ПК, где игра идёт
   дальше.

Сравнение с ПК (run15, тот же сценарий ввода, с телеметрией diag2): после закрытия `prologue.wmv` игра открывает
`shader\Decal.bnd`, `shader\SfxShader.bnd`, через ~40 с `sound\frpg2_sm1002.fsb` (звук локации — та самая вода),
затем ~50 с чёрного кадра, создаются 18 новых конвейеров и появляется 3D-сцена. Важно: **на ПК сцена тоже почти чёрная**
(средняя яркость кадра ~10/255, максимум 43; видна только после усиления яркости, с красным оттенком). То есть
«ПК-тест проходит» значит «кадры рисуются», а не «картинка нормальная»; тот же дефект освещения/тонмаппинга на
телевизоре выглядел бы как чёрный экран. Проверка `readback_resolve=fast` (как в nfsmw-nx) не закончена.

## Диагностическая сборка diag2 (только `app/`)

- `app/src/ds2_watchdog.{h,cpp}` — одна нить, просыпается раз в секунду; в основной лог:
  `[ds2 wd] … hb` каждые 2 с (vblank, шейдеры, последними привязанные командным процессором GPU, число потоков и
  файлов, память процесса), снимок всех гостевых потоков (lr/r1/r3/ctr/последний косвенный переход) и памяти раз в 10 с,
  `file +/-` (какие файлы игры открыты/закрыты — по ним видны этапы загрузки), `STALL` после 5 с без изменений.
  Лог сбрасывается после каждой записи.
- `app/src/ds2_switch_platform.{h,cpp}` — память процесса (`svcGetInfo`), гостевой backing, выключатель моста SaltyNX.
- cvars: `ds2_watchdog`, `ds2_watchdog_heartbeat_s`, `ds2_watchdog_snapshot_s`, `ds2_switch_saltynx` (по умолчанию
  false), `ds2_mesa_env` (переменные Mesa/NVK до создания Vulkan), `ds2_capture_save` (захват кадров без записи файлов,
  путь захвата относительно папки NRO).
- `ds2_dlc.cpp`: скрытые файлы `._*` пропускаются; время установки в логе.
- ПК: сборка и прогоны run15–run18 без ошибок; `ds2.toml` с плоскими ключами применяется (проверено run18).

План теста на консоли и список нужных файлов — `SW1_ds2/switch/diag2/TEST_PLAN.txt`.

## Результаты тестов 1–3 на консоли (diag2, логи `SW1_ds2/ds2_logs/diag2/toml1..3`)

Поведение у владельца одинаковое: Continue → загрузка → ролик → экран загрузки со звуком воды → выключение питанием.
По логам тесты различаются:

| | тест 1 (база) | тест 2 (`NVK_SWITCH_NO_UBO_CBUF=1` + `MESA_SHADER_CACHE_DISABLE=true`) | тест 3 (`vulkan_async_skip_incomplete_frames=false`) |
|---|---|---|---|
| конец лога после `frpg2_sm1002.fsb` (начало загрузки локации) | 1 с | 64 с | 1 с |
| `submission pressure` (таймаут `nvGpuChannelKickoff`, GPU не принимает работу) | 1 раз, за 0,4 с до конца лога | ни разу за весь запуск | 1 раз, за 0,6 с до конца лога |
| конвейеры на потоке GPU Commands, медиана интервала | 0,011 с (из дискового кэша Mesa) | 0,159 с, p90 1,1 с (без кэша) | 0,010 с |

Тест 2, период загрузки (профилировщик SDK): 0 fps, 0 kickoff и 0 fence за 50 с — на GPU ничего не отправляется;
поток GPU Commands занят на 52–62 % (сам синхронно создал 168 конвейеров: 123 только с вершинным шейдером, для них
асинхронного пути нет, и 45 заглушек), четыре потока создания конвейеров ~17–21 % каждый (~2 конвейера/с), главный
поток игры — 98 %. Шейдеры, привязанные командным процессором, меняются до последней строки: это медленный прогресс, а
не мёртвая блокировка. Дошла бы игра до картинки, неизвестно: питание выключено через ~1 мин после начала загрузки.

Ещё: на консоли ни разу нет строки `Created N graphics pipelines from Vulkan storage` (на ПК есть) — хранилище
конвейеров SDK между запусками не восстанавливается; вероятная причина — выключение питанием (данные, отданные файловой
системе, не зафиксированы). Дисковый кэш Mesa при этом сохраняется и сильно ускоряет (медиана 10 мс против 159 мс).

Вывод (гипотеза, не доказана): по умолчанию на загрузке локации GPU перестаёт принимать работу, и через секунду
логирование прекращается — похоже на зависание GPU/системы. С `NVK_SWITCH_NO_UBO_CBUF=1` (+ без кэша Mesa) этого нет.
Тесты 4 (`NVK_SWITCH_NO_UBO_CBUF=1` с кэшем) и 5 (только без кэша) разделяют эти два изменения; ожидание 10 мин и
проверка HOME отличают «медленно» от «зависла консоль».

diag3 (`out/app-switch/releases/diag3/`, sha256 `2de022b8…55b1`): + `logs/ds2_wd_last.txt` — последняя строка heartbeat
и последние события файлов, перезаписывается с `fsync` каждые 2 с и переживает выключение питанием.

## Тесты 4–5 (diag3) и сборка diag4

`logs/ds2_wd_last.txt` пережил выключение питанием в обоих тестах и совпал с концом основного лога — значит, обрыв лога
это момент остановки игры, а не потеря данных.

- Тест 4 (`NVK_SWITCH_NO_UBO_CBUF=1`, кэш Mesa включён): последний признак жизни 07:02:50, через 1 с после
  `frpg2_sm1002.fsb`, одновременно с `submission pressure`. Путь UBO не помог.
- Тест 5 (только кэш Mesa выключен): уровень загрузился, экран загрузки исчез (у владельца: чёрный экран и звук волн —
  та же тёмная сцена, что на ПК), игра рисовала мир: 0,3 → 1,4 fps, 412–571 вызовов отрисовки и 48–59 resolves на кадр,
  поток GPU Commands почти всё время ждёт fence (118 ожиданий, 983 мс в секунду) — GPU тратит ~0,7–1 с на кадр.
  Затем 20 `submission pressure` за 07:09:39–56 и остановка в 07:09:56; HOME показал только чёрный экран и выключил звук
  — GPU перестал работать и для системы.

Вывод (рабочий, не доказан окончательно): зависание GPU наступает, когда GPU выполняет настоящие шейдеры локации; с
кэшем Mesa это происходит сразу (шейдеры готовы), без кэша — после их компиляции. Не нехватка памяти (гостевая
516 МБ стабильна), не файлы (все открываются), не оверлей (выключен в тестах 1–5), не мост SaltyNX (выключен).

В закреплённом mesa-switch `1a8c1a66d6f` (+ патч nfsmw-nx) нет 61 более поздних коммитов upstream, среди них:
`f68a41350db horizon: fix GPFIFO submission capacity accounting`, `bfdbd1d / 6fb46f1 nvk: synchronize Horizon indirect
data before method headers`, `a72f9551e79 nvk: fix Horizon depth-stencil memory bindings`, `93d3ed1 nak: legalize
saturated long-immediate FADD on SM50`, `6db57fa nouveau/horizon: name the channel fault notifications`.

diag4 (`out/app-switch/releases/diag4-mesahead/`, sha256 `1631642c…703b`) — тот же код игры и приложения, Mesa =
mesa-switch `0ff52079ca9` (26.2.4) без патча nfsmw-nx, собрана тем же рецептом
(`MESA_DIR=…/mesa-switch-head NFSMW_PATCH=none SDK_OUT=…/mesa-sdk-head tools/switch/toolchain/build-mesa-nvk.sh`).
`out/app-switch` теперь сконфигурирован на `mesa-sdk-head`; предыдущие NRO — в `releases/`. Тест 6 — кэш Mesa в новой
папке (`MESA_SHADER_CACHE_DIR`, чтобы не взять шейдеры старого компилятора), тест 7 — без кэша.
