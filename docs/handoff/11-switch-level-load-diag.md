# 11. Switch: чёрный экран после вступительного ролика — разбор логов и диагностическая сборка

Ветка `diag/switch-level-load` (от `restore/build-env`). Рабочий NRO v1 (`e990a48`) сохранён:
`out/app-switch/releases/v1-e990a48/` и у владельца `SW1_ds2/switch/ds2.nro`. Диагностическая сборка —
`out/app-switch/releases/diag2/`, у владельца `SW1_ds2/switch/diag2/` (sha256 `be61e218…288b`).

## Что установлено по логам с консоли (`SW1_ds2/ds2_logs/`, три запуска v1)

Факты:

1. **Долгий первый запуск — установка DLC, а не шейдеры.** `ds2_001.log`: от `Loading STFS header file …/dlc/D4B91B6B…`
   (05:35:43) до `[ds2 dlc] install … -> 00000000` (05:38:52) — 3 мин 9 с распаковки пакета на SD. Во 2-м и 3-м
   запусках `already installed`. Рядом лежит `._D4B91B6B…` (файл AppleDouble от macOS): попытка установки кончается
   `Error reading STFS header: -32` — безвредно, в diag2 такие файлы пропускаются.
2. **Отчёт Atmosphère — процесс `ovlloader` (Tesla), модуль `Status-Monitor-Overlay`, не `ds2.nro`.** Тип `User Break`,
   причина Panic, результат `0x1159` = 2345-0008 = `LibnxError_NotInitialized`: оверлей сам вызвал
   `diagAbortWithResult`. Время в имени файла — 1792462199 = 05:09:59 MSK, на 25–50 мин раньше трёх запусков DS2
   (05:35, 05:52, 06:01). Связь с зависанием DS2 этим отчётом не подтверждается.
   Возможная точка взаимодействия есть: SDK (`sdk/src/ui/switch_saltynx.cpp`, из nfsmw-nx) по умолчанию подключается
   к порту SaltyNX `SaltySD` (одна сессия, нужна и оверлею), пишет блоки FPS/Reverse-NX в его общую память и временно
   отпускает `sm:`. Это не доказано как причина; в diag2 мост выключен (`ds2_switch_saltynx = false`).
3. **Все три лога обрываются, `rex_perfil.log` тоже.** Последняя строка `ds2_003.log` оборвана посреди строки
   (06:02:11); отчёты профилировщика SDK (поток с высшим приоритетом, раз в 10 с) кончаются на том же месте
   (~50 с после старта: 31 fps, 41 вызовов отрисовки на кадр, гостевая память 516/902 МБ). Значит, в этот момент
   остановился весь процесс (закрыт, убит или вся система повисла), а не только потоки игры: при дедлоке внутри игры
   профилировщик и сброс лога продолжали бы писать. Как именно закрывали игру, по логу не определить.
4. Перед обрывом: всплеск создания конвейеров Vulkan (`Creating graphics pipeline state …`) и предупреждения NVK
   `channel 2 hit native submission pressure (result=0xd5c)` = `LibnxNvidiaError_Timeout` от `nvGpuChannelKickoff`
   (очередь GPU не принимает работу): 64 раза в 05:39:30–32 (переход меню → ролик), 5 раз в 05:40:52 (за 3 с до
   обрыва `ds2_001`).
5. Ошибок шейдеров, Vulkan device lost, нехватки памяти, падений (`rex_crash.log`) в логах нет. Отсутствующие файлы
   (`KeyConfigParam.param`, `HollowLevelStatsParam.param`, `cache:\`, `install:\`) — те же, что на ПК, где игра идёт
   дальше.

Сравнение с ПК (run15, тот же сценарий ввода, с телеметрией diag2): после закрытия `prologue.wmv` игра открывает
`shader\Decal.bnd`, `shader\SfxShader.bnd`, через ~40 с `sound\frpg2_sm1002.fsb` (звук локации — та самая вода),
затем ~50 с чёрного кадра, создаются 18 новых конвейеров и появляется 3D-сцена. Важно: **на ПК сцена тоже почти чёрная**
(средняя яркость кадра ~10/255, максимум 43; видна только после усиления яркости, с красным оттенком). То есть
«ПК-тест проходит» значит «кадры рисуются», а не «картинка нормальная»; тот же дефект освещения/тонмаппинга на
телевизоре выглядел бы как чёрный экран. Проверка `readback_resolve=fast` (как в nfsmw-nx) не закончена.

## Диагностическая сборка diag2 (только `app/`)

- `app/src/ds2_watchdog.{h,cpp}` — одна нить, просыпается раз в секунду; в основной лог:
  `[ds2 wd] … hb` каждые 2 с (vblank, шейдеры, последними привязанные командным процессором GPU, число потоков и
  файлов, память процесса), снимок всех гостевых потоков (lr/r1/r3/ctr/последний косвенный переход) и памяти раз в 10 с,
  `file +/-` (какие файлы игры открыты/закрыты — по ним видны этапы загрузки), `STALL` после 5 с без изменений.
  Лог сбрасывается после каждой записи.
- `app/src/ds2_switch_platform.{h,cpp}` — память процесса (`svcGetInfo`), гостевой backing, выключатель моста SaltyNX.
- cvars: `ds2_watchdog`, `ds2_watchdog_heartbeat_s`, `ds2_watchdog_snapshot_s`, `ds2_switch_saltynx` (по умолчанию
  false), `ds2_mesa_env` (переменные Mesa/NVK до создания Vulkan), `ds2_capture_save` (захват кадров без записи файлов,
  путь захвата относительно папки NRO).
- `ds2_dlc.cpp`: скрытые файлы `._*` пропускаются; время установки в логе.
- ПК: сборка и прогоны run15–run18 без ошибок; `ds2.toml` с плоскими ключами применяется (проверено run18).

## Тесты 6–7 (diag4, новый Mesa) и сборка diag5

С новым драйвером нет ни одного `submission pressure`. Вместо этого на загрузке локации (тест 6: через 45 с после
`frpg2_sm1002.fsb`; тест 7: через 22 с и повторно через 50 с) драйвер не может создать буфер GPU 2 МБ:
`nvMapCreate(size=0x200000) failed: 0xce01` — 2001-0103 `KernelError_ResourceExhausted`; NVK делает это через
`memalign` + `nvMapCreate` + `svcSetMemoryAttribute` (`nouveau_horizon_memory.c`) — память из кучи выделилась, отказал
вызов ядра. Затем `VK_ERROR_OUT_OF_DEVICE_MEMORY`, `Failed to allocate 2097152 bytes of Vulkan upload buffer`, и
`Failed flush to file /switch/ds2/logs/ds2_001.log` — даже запись в файл перестаёт работать. Гостевая память при этом
516 МБ (стабильно).

Рабочая гипотеза: исчерпывается ресурс ядра процесса (блоки памяти / таблицы страниц / системный ресурс), а не память
игры. Тот же код 2001-0103 nfsmw-nx встречал при ~1,8 ГБ отображений и лечил ленивым отображением кусков гостевой памяти
в представления (`sdk/src/core/guest_memory_switch.cpp`: «the real ceiling on Horizon is the process limit on mappable
memory»). Кандидаты на рост у DS2: защита страниц для отслеживания записей в гостевую память (`RexGmProtect`, режим
«desmapeo» — каждая защищённая страница вырезается из каждого из пяти представлений по отдельности), буферы NVK с
изменёнными атрибутами, IPC. Со старым драйвером та же нехватка, видимо, выглядела как таймаут kickoff
(`resource_pressure` включает `InsufficientMemory`) с последующим зависанием.

diag5 (`out/app-switch/releases/diag5/`, sha256 `1007ec95…57ba`): heartbeat и снимки дополнены числом блоков памяти
процесса (обход `svcQueryMemory`), `InfoType_SystemResourceSizeUsed/Total`, кучей (`mallinfo`) и последним кодом
`RexGmLastResult`. Тест 8 — как тест 6; тест 9 — плюс `NOUVEAU_HORIZON_BO_CACHE_MB=16` и `nfsmw_io_rangos_mb = 0`.

`InfoType_SystemResourceSize*` = 0/0: у процесса нет собственного системного ресурса, объекты ядра для отображений
берутся из общего пула системы. За 4 с загрузки локации число блоков растёт на ~6000 при росте кучи на 17 МБ, а NvMap
создаётся единицы в секунду — значит, растут не буферы GPU. Отказы 2001-0103 начинаются около 10 000 блоков в обоих
тестах; после этого отказывают и другие процессы (запись файлов через FS, системный оверлей в тесте 9, HOME).

Вероятный источник (проверяется diag6): слежение за записью в физическую память для инвалидации текстур —
`Memory::EnablePhysicalMemoryAccessCallbacks` защищает диапазон в трёх представлениях (A0/C0/E0), а на Switch
`RexGmProtect` вырезает каждую защищённую страницу из представления через `svcUnmapProcessMemory`; каждый вырезанный
диапазон добавляет блоки, и при тысячах текстур локации их тысячи. `NOUVEAU_HORIZON_BO_CACHE_MB=16` и
`nfsmw_io_rangos_mb=0` (тест 9) продлили работу на ~25 с, но не изменили картину.

diag6 (`releases/diag6/`, sha256 `89934494…9e0b`): при каждом изменении числа блоков на 500 в лог и в
`ds2_wd_last.txt` пишется гистограмма блоков по (окно гостевой памяти / вне его, тип, права, атрибуты).

Растут отображения представлений гостевой памяти (зеркала A0/C0/E0…): объём тот же (~979 МБ), а блоков в 22 раза
больше. Дыр защиты мало, значит, рост — не сами защищённые страницы, а остатки: каждая страница, которую слежение за
записью вырезало (`svcUnmapProcessMemory`) и потом вернуло (`svcMapProcessMemory` на 4 КБ), остаётся отдельным блоком.
Число кусков гостевой памяти тоже растёт (~470 за загрузку), каждый даёт по блоку в каждом представлении.

**diag7 — правка SDK** (`sdk/src/core/guest_memory_switch.cpp`, оригинал в `/home/claude/backups/`):
- `RexGmProtect`: после возврата страниц вызывает `CoalesceViewRun` — непрерывный участок незащищённых страниц вокруг
  возвращённой (в пределах куска и представления) снимается одним `svcUnmapProcessMemory` и отображается снова одним
  `svcMapProcessMemory`, то есть становится одним блоком. Пропускается, если участок уже один блок; при неудаче —
  прежнее поэлементное отображение.
- `RexGmFaultIn`: если страница куска, уже отображённого в представлении, сейчас доступна (проверка `svcQueryMemory`),
  возвращает «повторить» — на случай, если другой поток попал в короткий промежуток перестройки.
- счётчики `RexGmCoalescedRuns/RexGmCoalesceFailures` → в heartbeat `merged_runs=`/`merge_fail=`.
Ожидаемый предел без дальнейших изменений: ~5 блоков на кусок + 2 на дыру, т. е. ~7 000 блоков на этой загрузке —
ниже наблюдаемого порога ~10 000, но с небольшим запасом; если не хватит, следующий шаг — крупнее куски гостевой памяти.
diag7: `releases/diag7/`, sha256 `6970f31f…50da`; тест 11 = настройки теста 9.

## Тест 11 (diag7) и сборка diag8

Правка diag7 сработала на то, на что была нацелена: блоков в окне гостевой памяти 800 вместо 7214
(`merged_runs=6687`, `merge_fail=0`), всего ~4400 блоков вместо ~10 800. Но в тот же момент (t=48 с, начало загрузки
локации) снова `nvMapCreate … failed: 0xce01` и `VK_ERROR_OUT_OF_DEVICE_MEMORY`. Значит, число блоков процесса было не
тем ресурсом, который кончается (или не единственным). Правку оставляем: она убирает накопление осколков без побочных
ошибок.

0xce01 = 2001-0103; в именах Atmosphère это `svc::ResultOutOfResource` (кончился объект ядра из slab-кучи), в libnx —
`KernelError_ResourceExhausted`. Следующий кандидат — память, которую libnx передаёт nvservices
(`__nx_nv_transfermem_size`, 8 МБ): там nvdrv ведёт учёт каждого объекта памяти GPU; nfsmw-nx упирался в неё
(«3585 текстур») и сделал настраиваемой (`nfsmw_switch_nvmap_mb`).

diag8 (`releases/diag8/`, sha256 `1df7ef37…6f4d`): cvar `ds2_switch_nvmap_mb` (выставляется в `OnPostInitLogging`, до

## Пересмотр: какой ресурс кончается (diag11)

Проба теста 17 меняла атрибуты страниц внутри уже разбитого 8-МБ буфера — она проверяла блоки памяти, но почти не
требовала новых таблиц страниц. Разбор исходников ядра Atmosphère (`libmesosphere`, `Kernel::InitializeResourceManagers`,
`KProcess::Initialize`) и загрузчика (`ldr_meta.cpp`):

- у процесса под hbloader нет своего системного ресурса (`sysres_kb=0/0` во всех логах): NPDM берётся из `hbl.nsp`
  (`system_resource_size` = 0), от исходной игры копируются только тип программы и пул памяти;
- такой процесс-приложение берёт блоки памяти из слэба приложений (20 000, наши ~4 500 — не предел), а **таблицы
  страниц — из общей с системными процессами кучи `s_page_table_heap`** (порядка 16–20 МБ на всю систему); там же
  общий слэб `KBlockInfo` на 4 000 записей;
- исчерпание общей кучи даёт `svc::ResultOutOfResource` (2001-0103) любой операции, которой нужна новая таблица, —
  у нас (`svcSetMemoryAttribute` при `nvMapCreate`) и у системы (FS при записи логов, HOME, оверлей). Это совпадает со
  всеми наблюдениями тестов 1–18.
- оценка нашей доли: у процесса ~4,8 ГБ отображений (куча 2,4 ГБ, представления 979 МБ, теневые 523 МБ, стеки
  733 МБ), ~3 300 границ блоков не на границе 2 МБ — до ~3 000 таблиц по 4 КБ (~12 МБ).

Обычные игры несут свой системный ресурс в NPDM. **diag11:**
- `hbl_ds2.nsp` — официальный nx-hbloader v2.4.5 с одной правкой NPDM: `system_resource_size = 0x4000000` (64 МБ);
  сборка `tools/switch/hbl-ds2/build.sh`. Включается без замены `hbl.nsp`: `[hbl_config] path=atmosphere/hbl_ds2.nsp`
  в `atmosphere/config/override_config.ini` (поддерживается `cfg_override`), откат — удалить строку.
- `ds2.nro`: проба `pt_left` (`ds2_watchdog_probe_tables`, по умолчанию 32): отображает по странице в отдельные пустые
  окна 2 МБ области стеков и сразу снимает — сколько новых таблиц страниц ядро ещё выдаёт; `pt_win=мин/макс` — окна
  2 МБ, которым нужна таблица.
- ПК: run24 (70 с, как run21) — без новых ошибок.
- Тест 19: `hbl_ds2.nsp` + `11-ds2.toml.test19`; тест 20: то же со стандартным `hbl.nsp` (для сравнения `pt_left`).
  NRO sha256 `40ebd056…734d`, `hbl_ds2.nsp` — в `releases/diag11/hbl_ds2.nsp.sha256`.

Если общий пул подтвердится, а 64 МБ не хватит — увеличить `system_resource_size` (до 0x1FE00000). План Б без
изменения hbloader: уменьшить число таблиц самого процесса (крупные непрерывные куски гостевой памяти, выровненные
по 2 МБ; меньше стеков потоков).

## diag12: меньше таблиц страниц у самой игры

Найдено при разборе libnx: второй аргумент `virtmemFindAslr/virtmemFindCodeMemory` — размер защитной зоны, а не
выравнивание. Окно гостевой памяти и все теневые отображения стояли на случайных адресах с шагом 4 КБ, поэтому ядро
не могло отобразить ни одно представление блоками по 2 МБ: таблица страниц на каждые 2 МБ. Плюс сотни мелких кусков
(`chunks`) на произвольных смещениях.

Правки SDK (`sdk/src/core/guest_memory_switch.cpp`, обоснование выше):
- окно и теневые отображения выравниваются по 2 МБ вручную (ищется место на 2 МБ больше);
